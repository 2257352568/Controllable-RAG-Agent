# 核心面试口述手册

这份手册只覆盖最容易决定面试走向的核心问题。练习时不要逐字背诵，统一使用：

> 结论 → 原理 → 项目实现 → 证据 → 边界

每个回答最后留出的“追问入口”，用于自然引出自己真正理解和实现过的内容，而不是堆技术名词。

## 1. 请用一分钟介绍项目

**口述答案：**

这是一个围绕 Agentic RAG 核心流程设计的学习型问答项目。基于开源 LangGraph 工作流，
我接入百炼模型和正文、章节摘要、原文引用三类索引，把规划、检索、证据判断、回答与拒答
连成可观察的闭环；答案需要绑定可回查证据，检索来源和调用预算也可以控制。

我重点验证“多一步 Agent 决策是否值得”：建立 direct、naive RAG、Agent 三条路径，
人工审核 52 道题，并记录答案质量、引用、Token、耗时和失败原因。已有分层结果反而显示
当前 Agent 不如 naive RAG；最近的小样本修复了一个无答案题空转，但多跳题仍会预算耗尽。
因此我会讲清架构选择与失败复盘，不会声称 Agent 已带来效果提升。

**追问入口：** 多源路由、plan/replan、逐句引用、三基线评测、调用预算。

**禁止说法：** “项目完全原创”“已经达到生产级”“准确率提升了 X%”。

## 2. 为什么普通 RAG 不够，为什么需要 Agent

**口述答案：**

普通 RAG 通常是一次 query、一次检索、一次生成，适合目标明确的单跳问题。复杂问题可能
需要拆成多个子问题，分别查询不同粒度的知识源，并根据新证据改变后续步骤，这才是
Agentic RAG 的价值。例如先从章节摘要定位情节，再从正文或 quotes 找可引用原文。

但 Agent 不是天然更好。它增加模型调用、延迟、错误传播和循环风险，所以项目设置 direct、
naive RAG、Agentic RAG 三组同题对照。目前已有探索性结果显示 naive RAG 更可靠、更便宜；
这也是我把失败案例和成本控制作为重点，而不是把“使用 Agent”本身当成绩的原因。

**追问入口：** 哪些题型需要多跳、如何做消融、Agent 失败时是否降级。

## 3. RAG 的完整链路是什么

**口述答案：**

离线侧是数据加载、清洗、切分、Embedding、索引构建与版本记录；在线侧是 query 处理、
检索、可选重排、上下文组织、生成、引用和拒答；最后用检索指标、回答指标、成本与延迟
做评测。权限、metadata、增量更新和可观测性贯穿全链路，不是生成完成后再补。

本项目使用 Qwen `text-embedding-v4` 的 1536 维向量和 FAISS，本地保存三个索引，并用
manifest 绑定模型、维度、文件大小和 SHA256，防止换 Embedding 后误用旧向量空间。

**追问入口：** 为什么换模型必须重建、FAISS 索引类型、离线与在线指标如何分开。

## 4. 为什么设计三类知识源

**口述答案：**

三类索引解决的检索粒度不同：summaries 适合先定位章节和全局情节，chunks 适合回答具体
事实，quotes 适合寻找精确措辞和可引用原文。分开索引后 Agent 可以根据子任务选择来源，
减少把所有内容同时塞进上下文造成的噪声。

代价是路由错误和额外复杂度，所以路由结果必须做枚举校验，禁用来源既在 Prompt 中说明，
也由图的条件边和检索节点强制。三源设计目前有控制流证据，但是否优于单一 chunks 仍应由
正式消融决定。

**追问入口：** 粒度、路由白名单、知识源消融。

## 5. chunk size 和 overlap 怎么选

**口述答案：**

chunk 太小会丢上下文并增加多片段拼接，太大会引入噪声、增加 Token，并可能降低精确定位；
overlap 用来缓解事实被切在边界的问题，但也会增加索引规模和重复召回。参数应该固定语料、
Embedding、问题集和 Top-K，通过检索召回、答案质量、Token、延迟一起选择。

当前 1000/200 字符是上游配置，不是我调出的最优值。审计显示 618 个 chunks 最大长度 999，
399 对同页相邻块的真实 overlap 是 117–199，P50 为 158，因为递归切分器会优先按分隔符
切割。离线 BM25 只用于筛选后续候选，不能替代 Qwen dense 实验。

**追问入口：** 为什么实际 overlap 不是固定 200、如何设计 chunk 消融。

## 6. Top-K 越大越好吗

**口述答案：**

不是。K 增大通常提高召回，但会降低上下文精度、增加 Token 和延迟，还可能让模型被无关
证据干扰。应画质量—成本曲线，并按知识源和问题类型选择，而不是只追求 Recall@K。

当前配置是 chunks=1、summaries=1、quotes=10。11 条可回答种子的冒烟中，K 增大提高了
多证据覆盖，但 precision 明显下降；由于样本小且标签只是 evidence-marker 代理，这只能
解释权衡，不能作为最优 K 结论。

**追问入口：** Recall/Precision、动态 K、为什么代理标签不等于人工 relevance。

## 7. cosine、dot product 和 L2 有什么区别

**口述答案：**

cosine 比较方向，忽略向量模长；dot product 同时受方向和模长影响；L2 比较欧氏距离。
如果向量都做了 L2 归一化，cosine、inner product 和 L2 的排序存在单调关系；未归一化时
不能混用。选择度量要遵循 Embedding 模型的训练方式和官方建议，并保证建库与查询一致。

当前 FAISS 是 `IndexFlatL2`，618×1536 的 chunks 索引做精确线性扫描，没有近似召回损失，
但规模增长后查询和内存成本线性增加。

**追问入口：** 向量归一化、Flat 与 ANN、维度相同为何仍不能混用模型。

## 8. LangGraph 相比普通 Chain 有什么优势

**口述答案：**

普通 Chain 更适合固定 DAG；Agent 需要条件分支、循环、共享状态、暂停恢复和明确终止。
LangGraph 把这些控制流显式化：节点读取 State、返回增量，条件边决定检索、回答或重规划，
checkpointer 可以按 thread 保存执行状态。

本项目的主流程是 anonymize→plan→deanonymize→任务拆解→路由→检索/回答→
answerability/预算判断；证据不足且预算充足才 replan，否则直接 final 或受控停止。优势不是
“用了图框架”，而是能看到每个决策点、预算和终止
原因，并能单独测试节点契约。

**追问入口：** State 设计、条件边、checkpoint、节点幂等。

## 9. 为什么先规划再重规划

**口述答案：**

初始 plan 把复杂目标拆成可执行子任务；每次检索后先判断证据是否充分。足够就回答，预算
耗尽就受控停止；只有证据不足且预算允许时，才让 replan 根据新证据调整剩余步骤。

风险是计划本身消耗 Token、可能漂移或陷入循环，因此必须限制步骤和模型请求，并与“一次
计划”甚至 naive RAG 做消融。项目已经实现控制流和终止保护，但尚没有正式数据证明
replan 带来净收益。

**追问入口：** 计划 schema、循环退出、如何评价 plan 质量。

## 10. 工具路由如何实现，路由错了怎么办

**口述答案：**

模型输出结构化的 tool 枚举，只允许 retrieve_chunks、retrieve_summaries、retrieve_quotes、
answer_from_context。代码不会直接信任字符串：先校验枚举和用户启用的来源，再由条件边
路由；非法或被禁用的选择会记录策略事件并把反馈交给 replan，而不是执行任意工具。

Prompt 约束只能降低出错概率，真正的安全边界必须在代码层。路由质量还应单独评测，例如
按题型统计正确来源、无效路由和额外步骤。

**追问入口：** structured output、Prompt 与代码约束的区别、工具最小权限。

## 11. 项目的“可控”体现在哪里

**口述答案：**

可控不是 temperature=0，而是用户和系统能限制“用什么知识、走多少步、花多少资源、何时
拒答”。项目支持三类来源开关、Top-K、最低有效证据数、最大步骤、Chat 请求和 Token
预算、Embedding 请求和输入数、累计 deadline、grounding 重试次数，以及机器可读终止原因。

调用预算在发送前预留，避免调用完成后才发现超限；来源限制既约束 Prompt，也约束实际图
路由。这里的实现是学习型单进程机制，不声称具备多副本全局配额或真正取消同步在途请求。

**追问入口：** soft/hard budget、timeout 与 cancellation、为什么 Embedding 单独计数。

## 12. 如何构建黄金评测集

**口述答案：**

先按真实失败模式设计题型，而不是随机凑数；再为每题定义 reference、可接受答案组、
answerable、证据片段和风险标签。正例必须定位到真实 supporting chunk，负例不能因为搜索
零命中就自动判定不存在，必须人工核验。

项目现在有 13 条种子和 39 条候选，共 52 条，覆盖单跳、推理、多跳、不可回答和对抗问题，
另有错误前提、注入、冲突和歧义等轻量风险标签。审核记录绑定题目 hash、语料 hash、
reviewer、checklist 和证据 chunk hash。当前真实进度以人审进度证据为准，所以它们仍不是黄金集。

**追问入口：** 为什么候选不能直接转 gold、负例怎样审核、数据版本如何绑定。

## 13. 为什么需要 direct 和 naive RAG 两个 baseline

**口述答案：**

direct 用来观察模型参数知识和记忆；naive RAG 用来测一次检索带来的收益；Agentic RAG 再
测规划、路由和循环的增量价值。只和 direct 比，无法知道收益来自检索还是 Agent；只展示
Agent 自己，也无法判断复杂度是否必要。

三组必须使用同一题集、模型配置和评判规则，并同时报告质量、错误率、P50/P95、Token 和
调用次数。最终可能得到“naive RAG 更划算”的结论，这同样是有效工程结论。

**追问入口：** 公平对照、控制变量、成本—质量 Pareto。

## 14. LLM-as-a-judge 有哪些偏差

**口述答案：**

常见偏差包括偏好与自己风格相近的答案、长度和措辞偏差、位置偏差、对同一错误与生成模型
产生相关判断，以及 temperature=0 仍可能有平台侧非确定性。裁判分数不能当绝对真值。

项目固定 judge schema，输入中明确区分问题、reference、证据和候选答案；正式协议要求
按 system/category 分层抽检至少 20%，比较人评分与模型分的容差一致率和 MAE。工具已完成，
但正式人评分尚未产生。

**追问入口：** 为什么不能随手抽样、同模型生成与裁判的问题、如何校准。

## 15. 如何证明提升具有统计意义

**口述答案：**

系统比较应按同一道题配对，因为题目难度差异很大。项目先对每个 case/system 的完整重复
取均值，再对同题差值做 case-level 配对 bootstrap，输出 95% CI；少于 20 对不做方向性
结论。重复运行还要报告 all-runs success 和终止/拒答一致性，不能用一次成功截图代表稳定。

统计显著也不等于业务有意义，所以还要看效应量、绝对质量和成本。52 条人审已完成，
但固定模型的全量正式结果仍未完成；已有分层结果不能合并，也不能声称显著提升。

**追问入口：** 为什么配对、bootstrap 假设、显著性与实际价值。

## 16. 为什么选择 Qwen，OpenAI-compatible 意味着什么

**口述答案：**

选择百炼是因为当前使用该平台密钥，兼容接口便于复用 LangChain SDK。项目默认聊天模型
配置为 `qwen3.8-max`，Embedding 是 `text-embedding-v4`；最近的有界回归使用百炼提供的
`deepseek-v4-pro-0813`，不同生成模型的评测结果始终分开记录。

OpenAI-compatible 只表示 API 形状大体兼容，不代表参数、structured output、tool call、
Token metadata 或错误语义完全一致。迁移时曾遇到 thinking 与 tool_choice 组合导致 400，
说明必须做最小真实请求和端到端验证。代码使用兼容 SDK 作为传输层，不使用 OpenAI 模型。

**追问入口：** 模型迁移、结构化输出差异、为什么 Embedding 也必须重建。

## 17. 如何处理模型超时、重试、限流和熔断

**口述答案：**

timeout 限制单次等待；retry 处理少量瞬时失败；rate limit 控制进入系统的流量；circuit
breaker 在下游持续故障时快速失败，防止雪崩；fallback 是经过质量验证后的降级路径。它们
解决的问题不同，不能互相替代。

项目设置 SDK timeout，评测外层只重试网络、429 和 5xx 等瞬时错误，永久参数/鉴权错误立即
失败；进程内熔断器支持 closed/open/half-open；API 有并发准入。边界是暂未统计 SDK 内部
HTTP attempts，也没有跨进程全局熔断，这些只作为生产化讨论，不继续扩建。

**追问入口：** 指数退避、幂等、重试风暴、half-open。
